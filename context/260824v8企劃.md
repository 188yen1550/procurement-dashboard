## 一、系統定位（不變的最高原則）

> **系統只負責「整理資料、給建議」，商品最終要不要賣，永遠由人來按下核准。**

```
資料蒐集 → 規則式評估 → 加權計分 → AI輔助分析 → 人工審核 → 正式選品決策
```

AI的角色僅限於：趨勢資料分析、AI摘要、推薦原因、風險提示、核心客群匹配輔助、協助發現潛在候選商品。**最終核准與否，永遠由人工審核決定。**

### ⚠️ 重要提醒：核准（APPROVED）≠ 已銷售

`review_status`（審核狀態欄位）中的`APPROVED`（已審核通過）僅代表：**此商品通過選品評估與人工審核，被列入可執行團購銷售的候選名單**。

它**不代表**：已正式上架銷售／已與供應商完成議價或簽約／已產生實際訂單或營收。

「核准」是本系統**選品決策的終點**，不是**銷售執行的起點**。核准後的議價、上架、實際開團等商業動作，屬於團購營運下一階段的決策範疇，不在本系統範圍內。此定義需在儀表板、審核頁UI文案、以及demo口頭說明中一致呈現。

### ⚠️ 命名區隔提醒：`pricing_type` vs `product_type_id`

兩個欄位中文都可能被稱為「商品類型」，但語意完全不同，開發與文件中須嚴格區分：

| 欄位 | 代表意義 | 值 |
|---|---|---|
| `pricing_type` | 訂價分流（QA1原始設計） | `NEW`（新品）／`RESALE`（再販售） |
| `product_type_id` | 商品實際分類（架構v3原始設計） | FK關聯`product_types`表，例如食品/日用品等 |

`pricing_type`為避免與`product_type_id`混淆而特別命名，非架構v3原始欄位名稱。

```
    │   │       └── 備註：命中標籤為清單式元件，每列是「標籤輸入框＋命中等級下拉
    │   │           （核心／一般／弱）」，可增列刪列，非單一純文字框——每個標籤
    │   │           需逐一指定等級，對應五-15 festive_campaign_tags
    │   ├── 檔期狀態（UPCOMING／PREPARING／ACTIVE／EXPIRED，Daily Cron自動判斷）
    │   └── 手動切換狀態（獨立入口，不放進編輯Modal）
    │       └── 備註：
    │           1. 小型獨立視窗，選目標狀態（四選一）＋開關is_manual_override
    │           2. 與「編輯」拆成兩個按鈕，避免使用者誤以為編輯儲存即等於切換狀態
    │           3. 熔斷清單②備援機制，Daily Cron停用時管理層可手動切換
    │
    └── 帳號管理
        ├── 帳號列表（username／name／角色／啟用狀態）
        ├── 新增帳號（指定username／name／角色與初始密碼）
        └── 停用帳號
            └── 備註：
                1. 本系統不開放公開自我註冊，帳號一律由管理層代辦建立
                2. 只提供停用、不提供實體刪除——帳號被審核紀錄等歷史資料參照，
                   實體刪除會使稽核軌跡失去對應人員
                3. 帳號管理權限目前由MANAGER兼管，未獨立SYS_ADMIN角色，
                   理由與未來調整條件見七-5
```

**角色權限對照**（顯示名稱，DB代碼不變）：`PURCHASER`＝**操作**（操作層／操作人員）／`MANAGER`＝**管理**（管理層／管理人員）。「選品審核」與「設定」選單僅**管理**可見，其餘功能操作／管理皆可使用。

## 三、前端頁面與API對照

> 用途：前後端分工時，前端可據此確認「這個畫面要接哪幾支API」，後端可反向確認「這支API少做了會讓哪個畫面開天窗」。所有端點的完整功能說明見四、API總表。
>
> ⚠️ 一個畫面通常需要多支API組合，其中**分數相關資料的來源有雙軌規則**：已審核通過（`review_status=APPROVED`）的商品，分數改讀`review_records`的Snapshot凍結值；其餘狀態讀`product_evaluations`即時值。此規則封裝在後端`ScoringService`內，前端一律呼叫同一支API即可，回應中的`dataSource`欄位（`SNAPSHOT`／`LIVE`）標明本次數字的來源軌道。

### 3-1 登入頁

| 畫面元素／動作 | API | 備註 |
|---|---|---|
| 送出登入 | `POST /api/auth/login` | 成功後Token寫入httpOnly Cookie |
| 頁面載入時取得自身身分 | `GET /api/auth/me` | 用於判斷選單顯示範圍（操作／管理） |
| 登出按鈕 | `POST /api/auth/logout` | |

### 3-2 儀表板

| 畫面元素 | API | 備註 |
|---|---|---|
| 統計卡片（總數／待審／通過／拒絕） | `GET /api/dashboard/statistics` | |
| AI推薦 Top 10 | `GET /api/dashboard/recommendations` | 含重新入榜標籤與上次拒絕留言 |
| 高風險示警 | `GET /api/dashboard/risk-alerts` | AI風險提示文字命中`alert_keywords`者 |
| 選品轉換率 | `GET /api/dashboard/conversion-rate` | 分母為0時回傳null，前端需處理「尚無資料」狀態 |

> 四支API彼此獨立，可並行呼叫；任一支失敗只影響對應卡片，不應讓整頁空白。

### 3-3 品項管理｜主清單

| 畫面元素／動作 | API | 備註 |
|---|---|---|
| 清單載入、搜尋／篩選／分頁 | `GET /api/products` | 支援keyword／三種狀態／類型／分頁參數 |
| 「AI建議」分頁籤 | `GET /api/products/ai-suggested` | 與主清單分開，只顯示`AI_SUGGESTED` |
| 新增品項（表單的類型下拉選項） | `GET /api/settings/product-types` | 需先載入才能渲染下拉 |
| 新增品項（送出） | `POST /api/products` | |
| 加入候選（AI建議清單的動作） | `POST /api/products/{id}/promote-to-candidate` | `AI_SUGGESTED` → `CANDIDATE` |

### 3-4 品項管理｜品項詳情頁

> 本頁子區塊最多、需要的API也最多，是前後端銜接最容易漏接的一頁。

| 畫面區塊 | API | 備註 |
|---|---|---|
| 基本資料、狀態標籤 | `GET /api/products/{id}` | |
| 商品圖片顯示 | 併於`GET /api/products/{id}`回應（`imageUrl`）| 無圖片時`imageUrl`為null，前端顯示預設圖或Empty狀態，不阻擋其他區塊渲染 |
| 上傳／更換圖片按鈕 | `POST /api/products/{id}/image` | `multipart/form-data`，欄位名`file`；成功後回傳的`imageUrl`為Spring自行伺服的相對路徑，可直接接`<img src>` |
| 資料完整度、六大分項分數、Base Score | `GET /api/products/{id}/evaluation` | 回應含`dataSource`標明雙軌來源 |
| 目前評估模式與權重顯示 | `GET /api/settings/evaluation-mode/current` | 若要展開權重明細再呼叫`/evaluation-modes/{id}/factors` |
| 節慶加成明細（命中檔期、Match Weight、Urgency Factor） | `GET /api/products/{id}/festival-boost` | 未命中時`matchedCampaign`為null，前端不顯示此區塊 |
| 趨勢資料、資料新鮮度 | 併於`GET /api/products/{id}/evaluation`回應 | 手動同步按鈕另呼叫`POST /api/products/{id}/trend/sync` |
| 市價與團購價比較 | 併於`GET /api/products/{id}`回應（`market_price`） | 僅RESALE商品顯示 |
| AI摘要／推薦原因／風險提示 | `GET /api/products/{id}/ai-analysis` | 無快取時回傳空物件（非404），前端顯示Empty狀態 |
| 重新產生AI分析按鈕 | `POST /api/products/{id}/ai-analysis/generate` | 有API成本，需二次確認 |
| 審核歷史 | `GET /api/products/{id}/reviews` | |
| 編輯（送出） | `PUT /api/products/{id}` | 整份覆蓋；核准後改選品核心資料會回409 |
| 刪除 | `DELETE /api/products/{id}` | 僅未曾送審者可刪 |
| 重新送審 | `POST /api/products/{id}/resubmit` | 僅`REJECTED`可用 |
| 封存／復用 | `POST /api/products/{id}/archive`、`POST /api/products/{id}/restore` | |

### 3-5 選品審核（僅管理）

| 畫面元素／動作 | API | 備註 |
|---|---|---|
| 待審清單 | `GET /api/reviews/pending` | 預設「未審核＋使用中」 |
| 審核頁完整資訊（分數、節慶加成、AI摘要、風險選項清單） | `GET /api/reviews/{productId}` | 一支API回傳整頁所需資料，含可勾選的風險選項 |

## 四、API總表

> 每支API均標示角色權限：`[操作+管理]`代表操作／管理皆可呼叫；`[僅管理]`代表僅MANAGER角色可呼叫，後端須以Spring Security `@PreAuthorize`等method security機制落實，不可僅靠前端選單隱藏（見七-4安全性備註）。

```
API
│
├── 1. 登入／權限
│   ├── POST /api/auth/login [公開，無需登入]
│   │   └── 功能：驗證帳號密碼、建立JWT Token、取得使用者角色
│   ├── GET /api/auth/me [操作+管理]
│   │   └── 功能：取得目前登入使用者的基本資料與角色
│   └── POST /api/auth/logout [操作+管理]
│       └── 功能：登出，前端清除本地Token；為未來若需token黑名單機制預留擴充點
│
├── 1-2. 帳號管理 [僅管理]
│   │   └── 前提：本系統不開放公開自我註冊，一律由管理層代辦建立
│   │       （Admin Provisioning，理由見七-5帳號建立與角色劃分決議）
│   ├── GET /api/users [僅管理]
│   │   └── 功能：列出所有帳號（含角色、啟用狀態），不回傳密碼雜湊值
│   ├── POST /api/users [僅管理]

│   ├── GET /api/dashboard/statistics [操作+管理]

│   └── GET /api/dashboard/conversion-rate [操作+管理]
│       └── 功能：計算選品轉換率（公式定義見二、前端功能樹狀圖之「選品轉換率」節點）
│
├── 3. 品項管理
│   ├── GET /api/products [操作+管理]
│   │   └── 功能：依關鍵字、審核狀態、品項狀態、候選狀態、商品類型等條件查詢品項

│   │   └── 功能：取得candidate_status=AI_SUGGESTED的AI建議清單

│   ├── POST /api/products/{id}/image [操作+管理]【新增】
│   │   └── 功能：上傳／替換商品圖片，multipart/form-data格式，欄位名為file
│   │       └── 備註：僅支援jpg／jpeg／png／webp，單檔上限5MB；imageUrl為選填欄位，
│   │           不上傳圖片不影響商品建立與送審；儲存與安全性設計見七-6
│   ├── GET /api/products/{id} [操作+管理]
│   │   └── 功能：取得商品基本資料、核心資料、資料完整度、評估、趨勢、AI及風險等資訊
```

### 2. products（商品資料表）

```

├── pricing_type(ENUM、NOT NULL)：商品分流【QA1新增】
│   ├── NEW：新品
│   └── RESALE：再販售
├── name(VARCHAR(100)、NOT NULL)：商品名稱
│   └── 備註：**刻意不設唯一約束，允許重複商品名稱**（已與團隊確認，非疏漏）。
│       同名商品可能來自不同供應商、不同規格、不同批次進貨（例："A供應商的
│       雞腿禮盒"與"B供應商的雞腿禮盒"），強制唯一會連帶擋掉這些合法情境。
│       真正該防的「操作人員手滑重複送出同一筆」風險，交由**前端**處理
│       （送出後禁用按鈕、debounce、或偵測到同名時跳出確認提示），不由後端
│       用「一律禁止同名」這種對所有情境都生效的規則來擋——那是用治療症狀的
│       方式犧牲掉本來合法的使用情境。若未來確認商品名稱在實務上就是唯一
│       識別品項、同名一定是誤操作，需要應用層查詢檢查與DB層UNIQUE約束
│       兩者一起補上，不能只加其中一層（詳見ProductService.createProduct()）

│       POST /api/products/{id}/image上傳實際檔案，由後端驗證並寫入
│       一個Spring自行伺服的相對路徑（例："/images/products/{uuid}.jpg"）；
│       ⚠️目前POST／PUT /api/products的imageUrl欄位【仍是一般字串欄位，
│       未鎖定為唯讀】，理論上仍可直接傳入任意字串（例如外部圖床連結）覆蓋掉，
│       未強制要求圖片一定要走上傳驗證流程——這是刻意保留的彈性（開發測試階段
│       方便直接貼外部圖片網址），還是應該收斂成「只能透過上傳端點設定」，
│       屬於待決議事項，見十五-3。設計與安全性討論見七-6
├── supplier_name(VARCHAR(100))：供應商名稱
├── cost_price(DECIMAL(10,2)、NULLABLE)：商品成本價格
│   └── 備註：新品(NEW)可為空，待議價完成後回填【QA1】
├── sale_price(DECIMAL(10,2)、NULLABLE)：預計銷售價格
│   └── 備註：新品(NEW)可為空【QA1】

│   └── 備註：僅RESALE（再販售）商品填寫，NEW（新品）不適用（尚無實際市場對照價）。
│       獨立新增而非借用既有欄位的原因：cost_price是B2B進貨成本、sale_price是團購賣價，
│       兩者語意上都不等於「消費者一般通路購買價」，若overload雙重語意會造成
│       日後API/UI/報表難以區分情境。此欄位不進入評分公式（見六、QA2）
│   └── 備註：僅RESALE商品填寫，NEW商品不適用；不進評分公式，僅供品項詳情頁

│   ├── AI_SUGGESTED：AI建議，非正式候選（僅由AI批次選品產生，見POST /api/products/ai-suggested/batch-generate）
│   └── CANDIDATE：正式候選，進入評分排行
```

### 4. evaluation_modes（評估模式版本表）

```
├── id(BIGINT、PK)：評估模式版本唯一識別碼
├── mode_code(VARCHAR(30)、NOT NULL)：評估模式代碼
│   ├── BALANCED：均衡模式
│   ├── VOLUME：衝量模式
│   └── PROFIT：高利潤模式
├── mode_name(VARCHAR(50)、NOT NULL)：評估模式顯示名稱
├── version(INT、NOT NULL)：模式版本
├── description(TEXT)：模式用途與特性說明
├── is_active(BOOLEAN、NOT NULL、DEFAULT TRUE)：此版本是否可使用
├── created_at(DATETIME、NOT NULL)
└── created_by(BIGINT、FK)
```

**核心概念**：權重修改不覆蓋既有資料，而是建立新版本，確保歷史審核結果可追溯。

**⚠️「目前生效模式」不等於`is_active`**：`is_active`的語意是「此版本是否可用（未棄用）」，同時可能有多筆`is_active=TRUE`（BALANCED／VOLUME／PROFIT三套模式各自都有可用版本）。全系統實際套用哪一套，是另一件事，儲存於`system_settings`（見五-14），不要誤用`is_active`或`id`大小去猜測目前生效模式。

**3套模式權重草案**（供審核，非依實際銷售數據校準）：

| 模式 | BUSINESS | AUDIENCE | HISTORY | FORECAST |
|---|---|---|---|---|
| 均衡模式(BALANCED) | 25% | 25% | 25% | 25% |
| 衝量模式(VOLUME) | 15% | 30% | 15% | 40% |
| 高利潤模式(PROFIT) | 45% | 15% | 15% | 25% |

### 節慶加成計分規則

```
Final Score = Base Score + Festival Boost
Festival Boost = Match Weight × Urgency Factor × Boost Cap上限（暫訂+5，絕對分數）
```

- **Match Weight**（標籤命中權重係數）：核心命中1.0／一般命中0.6／弱命中0.3／未命中0，多標籤取最高等級不加總
- **Urgency Factor**（時間緊迫係數）：
  - 節日型(FESTIVAL)：PREPARING期間線性遞增(1－剩餘天數/準備天數)，ACTIVE固定1.0
  - 季節型(SEASON)：PREPARING固定0.2（不遞增），ACTIVE固定1.0
- **多節慶重疊**：取最大值(MAX)，不加總套Cap
- **不命中不扣分**：Festival Boost=0，不影響原本評分
- **已審核通過商品**：Final Score凍結於Snapshot，不隨後續趨勢更新重算
- **命中判定**：商品`campaign_tags`(split(",")後)與當前啟用檔期在`festive_campaign_tags`底下的`tag`做集合交集運算，有交集即判定命中，並取命中標籤中`match_tier`等級最高者作為該檔期的Match Weight；**僅比對`campaign_status IN (PREPARING, ACTIVE)`的檔期**，`UPCOMING`（尚未備戰）與`EXPIRED`（已結束）的檔期不參與Festival Boost計算，即使標籤有交集也視為未命中

### 15. festive_campaign_tags（檔期標籤命中權重明細表）

```
├── id(BIGINT、PK)：唯一識別碼
├── campaign_id(BIGINT、FK、NOT NULL)：對應檔期(festive_campaigns)
├── tag(VARCHAR(50)、NOT NULL)：標籤內容(例：bbq)
├── match_tier(ENUM、NOT NULL)：標籤命中權重層級
│   ├── CORE：核心命中，Match Weight = 1.0
│   ├── GENERAL：一般命中，Match Weight = 0.6
│   └── WEAK：弱命中，Match Weight = 0.3
└── created_at(DATETIME、NOT NULL)
```

**唯一約束**：`(campaign_id, tag)`——同一檔期對同一標籤只能有一種分級，於資料庫層防呆，應用層不需自行檢查重複。

**存在原因**：節慶加成計分規則的Match Weight定義了核心／一般／弱三個命中等級，但等級是「每個標籤各自」的屬性——同一個檔期底下，`bbq`可能是核心命中、`gift`只是一般命中。原本設計以`festive_campaigns.target_tags`單一逗號分隔字串存放標籤，該欄位只能表達「有哪些標籤」，無法表達「每個標籤是哪一級」，導致Match Weight的三層規則無資料可依循，只能退化成「有交集就算命中」的二元判斷。拆為獨立關聯表後，每個標籤都能各自帶一個`match_tier`，計分規則才真正可實作。

**與products.campaign_tags的比對方式**：商品端維持單一逗號分隔字串（商品只需宣告「我有哪些標籤」，不需要分級），比對時取`products.campaign_tags`與本表`tag`的交集，命中多個標籤時取其中`match_tier`等級最高者作為該檔期的Match Weight，不累加（見節慶加成計分規則）。

## 六、QA修正落地設計摘要

### QA1｜毛利判定邏輯（新品 vs 再販售）

`pricing_type`：`NEW`（新品）／`RESALE`（再販售）。新品不要求成本價/售價欄位，狀態為`PENDING_PRICING`（待訂價），評分引擎以該類別歷史中位數代入，不因欄位空白被扣分；再販售正常帶入定價欄位並計算毛利率。

### QA2｜市售價格 vs 團購價格的吸引力評估

不疊加進總分公式（避免跟毛利率因子重複計分），做成品項詳情頁AI分析區塊的呈現層量化洞察（折扣率、消費者實際入手成本）。所需的「市售價格」為`products.market_price`欄位，僅RESALE商品填寫（欄位設計理由見五-2）。

### QA3｜資料完整度60%門檻的計算範圍

門檻分母只計算操作層建立商品當下有能力自主填齊的欄位，依`pricing_type`動態調整；未達門檻不進入固定評估模式計分、不進入AI推薦Top10，列表狀態顯示「資料待補」，仍允許編輯補齊。

### QA4｜AI主動選品的定位

`candidate_status`：`AI_SUGGESTED`（AI建議，非正式候選，僅由AI批次選品排程產生）→ 操作人員手動「加入候選」→ `CANDIDATE`（正式候選，才進入評分排行）。**操作人員手動新增品項預設直接為`CANDIDATE`**（非AI_SUGGESTED，修正原設計語意矛盾——手動輸入的商品不是「AI建議」）。只有`CANDIDATE`狀態商品才會出現在品項清單、分數排行、推薦清單裡。

### QA5｜本地LLM vs API串接LLM

**結論：維持API串接**，團隊規模與時程都不具備自架LLM的條件；搭配「AI內容預先生成並快取」機制因應現場風險。架構上仍以Service層抽象介面（`LlmAnalysisService`）隔離廠商依賴，換模型只需改一個實作類別，不因廠商已定案而放棄此抽象層。

**廠商與預算**：

| 項目 | 內容 |
|---|---|
| 廠商／模型 | GPT-5.6 Luna（OpenAI GPT-5.6系列最低成本／最快速版本） |
| 定價（查證日期2026/08） | Input $0.20／1M tokens、Output $1.20／1M tokens、快取輸入$0.02／1M tokens |
| 支援能力 | Structured Outputs／JSON Mode、Function Calling；標準API Key認證 |
| 月度預算上限 | $20美金以下 |

**用量保護機制**：`LlmAnalysisService`呼叫LLM前先檢查本月累積呼叫次數，超過自訂安全值（例如500次）即跳過呼叫並回傳「本月AI分析用量已達上限」，另搭配OpenAI後台Monthly budget limit作為第二層硬上限。此保護邏輯工時併入原「LLM API串接」2.5天內，不另編列。

**已知限制（刻意技術債）**：`evaluation_modes`只有讀取（GET）API，沒有新增／修改模式本身的寫入API——本階段調整這張表的資料一律採直接改DB種子值（seed script）方式處理，待Phase 2視需求評估是否補管理介面。註：`PUT /api/settings/evaluation-mode/current`不屬於此限制範圍，它改的是`system_settings`裡「目前指向哪個既有模式」的指標值，不新增或修改`evaluation_modes`表本身的資料列。

`risk_options`**不在**此限制範圍內：管理層需要能自行新增自訂風險類型（含`alert_keywords`），故提供`POST /api/settings/risk-options`寫入API，見四、API總表七-2。這是本階段與`evaluation_modes`處置不同的地方——評估模式的權重調整牽動所有商品的分數計算、需要版本控管，風險選項只是審核時的複選項目，新增一項不影響任何既有分數，開放寫入的風險與成本都低得多。

## 七、風險示警與決策回饋設計決議

### 7-1 三項功能的效益/複雜度比較

| 功能 | 效益 | 複雜度 | 原始工時估算 |
|---|---|---|---|
| 風險示警中心（獨立監控系統） | 中，但demo現場很難剛好展示到觸發時刻 | 高（規則引擎+排程+UI） | 4-5天 |
| 決策紀錄與回饋閉環 | **最高**，是驗證「AI輔助決策」定位的證據來源 | 中偏高 | 3-4天（簡化版） |
| 報表中心 | 最低，demo現場很少被檢視 | **最高**（PDF中文字型是Java生態老坑） | 3-4天（且風險不可控） |

### 7-2 最終決議：風險示警中心（獨立監控系統）不做

改用AI風險提示（唯讀顯示於品項詳情）→ 管理層審核時閱讀 → 人工風險評估（複選）→ 審核留言，風險溝通在審核當下一次處理完，不需要獨立、24小時背景運作的示警系統。改用「已審核拒絕商品重新入榜提醒」機制取代其展示效果（見二、前端功能樹狀圖之AI推薦Top10）。

### 7-3 決策紀錄（保留）

`review_records`本來就是審核功能的必要產物，真正的增量成本只有一個「決策紀錄列表」查詢畫面。**準確度統計分析（如Pearson相關係數、A級命中率%）不做**——雛型階段樣本數不足，留待Phase 2累積真實資料後再做。

### 7-4 安全性設計（RBAC落實／併發控制／JWT）

**RBAC後端落實**：三、API總表已逐支標示`[操作+管理]`／`[僅管理]`角色權限，前端選單隱藏僅是體驗優化，**後端須以Spring Security method security（如`@PreAuthorize("hasRole('MANAGER')")`）逐支落實**，避免Broken Access Control（OWASP API1/API5）風險，尤其`POST /api/reviews`與所有`/api/settings/*`必須鎖死僅`MANAGER`角色可呼叫。此為W1「登入/RBAC」既有工時範圍內的必要工作項，非新增工時。

**審核併發控制**：`POST /api/reviews`寫入前，Service層以條件式UPDATE（`UPDATE products SET review_status=? WHERE id=? AND review_status='PENDING'`）更新狀態，若影響筆數為0（代表已被他人審核過）回傳409 Conflict，避免同一品項被重複審核造成狀態競態。**不採用樂觀鎖版本欄位**（不新增`products.version`），因為完整樂觀鎖需要前後端配套的版本傳遞與衝突處理UI，對6週時程屬於過度工程化；條件式UPDATE可達到同等防護效果，且僅需Service層一行SQL改動。

**JWT設定**：

| 決策項目 | 採用方案 |
|---|---|
| Token儲存位置 | httpOnly Cookie優先；若實作複雜度過高可退而求其次採記憶體內變數，**不使用**localStorage/sessionStorage（防XSS竊取） |
| 過期時間 | 8小時（對應一個工作天），demo環境可視情況調整 |
| Refresh Token | **不實作**完整輪替機制，過期後直接要求重新登入，避免正式產品級複雜度（黑名單/輪替偵測），列入Phase 2待辦 |
| 登出端點 | 補上`POST /api/auth/logout`，即使JWT本質無狀態、單純登出效果有限，仍維持語意完整性並為未來黑名單機制預留擴充點 |
| DB Schema影響 | 不需新增欄位，維持JWT無狀態設計 |
| Token過期流程 | 任何頁面偵測到401 → 導回登入頁＋保留原本操作提示（例如「請重新登入後繼續操作」），呼應8小時過期、無Refresh Token的設定 |
| Cookie Secure屬性 | 由設定檔`cookie.secure`控制，非寫死於程式碼。正式環境（HTTPS）為`true`；本機開發若跑在`http://localhost`需設為`false`，否則瀏覽器不會帶上Cookie，等同於無法在開發階段驗證「瀏覽器自動帶Cookie」這條真實路徑。程式碼端預設值取`true`（安全預設），設定漏填時走安全的那一邊 |

### 7-5 帳號建立與角色劃分決議

**帳號建立方式：管理員代辦（Admin Provisioning），不開放公開自我註冊。**

本系統為內部採購團隊使用，使用者身分需與實際任職狀態一致，開放自我註冊會失去這層控制。因此不提供註冊端點，帳號一律由管理層透過三、API總表「1-2. 帳號管理」新增。第一個`MANAGER`帳號由種子資料（SQL seed）建立，解決「沒有帳號就無法建立帳號」的先有雞先有蛋問題。

**帳號只停用、不刪除**：`app_users`被`review_records.reviewer_id`、`products.created_by`等欄位參照，實體刪除會使歷史稽核紀錄失去對應人員資料。停用（`enabled=false`）即可達成「此人不再能登入」的目的，同時保留稽核軌跡完整性。

**角色劃分：帳號管理權限由`MANAGER`兼管，不另設獨立`SYS_ADMIN`角色。**

嚴格來說，「審核商業決策」與「管理系統帳號」是兩種不同性質的職責，理想上應由不同角色承擔——若`MANAGER`帳號遭盜用，攻擊者不只能竄改審核結果，還能自建後門帳號，即使原帳號事後停用後門仍在，違反最小權限原則。

但在本階段的實際條件下仍選擇由`MANAGER`兼管，理由是：6週雛型、小型內部採購團隊，`MANAGER`實質上就是那幾位主管，與「系統管理員」是同一批人。此情況下職責分離換來的是「理論上正確、但沒有實際降低風險」（操作的人本來就相同），純粹多一層權限矩陣的複雜度，屬於過度工程化（違反YAGNI）。

考量過但未採用的替代方案：

| 方案 | 做法 | 未採用原因 |
|---|---|---|
| 新增獨立`SYS_ADMIN`角色 | `app_users.role`擴充為三個值，帳號管理API改認`SYS_ADMIN` | 職責分離最徹底，但如上所述本階段換不到實際風險降低；且需再解決一次「第一個`SYS_ADMIN`帳號怎麼生」的問題 |
| 疊加`is_system_admin`布林旗標 | 不動`role`語意，另開欄位標記「這個MANAGER同時能管帳號」 | 權限判斷要同時檢查角色＋旗標兩個欄位，邏輯比單一`role`複雜，日後角色再擴充容易越疊越亂 |

**觸發重新評估的條件**——出現以下任一情況時，應重新討論是否改採獨立`SYS_ADMIN`角色：

- `MANAGER`人數明顯增加，且分屬不同部門／單位
- 出現跨部門、彼此不完全信任的多位`MANAGER`
- 出現明確的外部資安／法遵要求，規定業務角色不得兼帳號管理權限

**未來若改採獨立角色的異動範圍**（已預先確認，供屆時評估成本用）：`JwtTokenProvider`／`JwtAuthenticationFilter`將角色視為純字串、不寫死角色名稱，因此耦合範圍可壓到最小——需異動的僅有`app_users.role` ENUM定義、`UserRole.java`列舉，以及新增一組獨立的帳號管理垂直切片與前端路由；既有的登入／`me`／登出、審核評估功能、前端既有頁面皆不受影響。

### 7-6 商品圖片儲存設計決議

**現況**：`products.image_url`欄位在原始規劃裡只有「存一個字串」這個資料庫設計，完全沒有規劃「這個字串從哪裡來」——沒有檔案上傳端點、沒有儲存機制、沒有靜態資源伺服設定。企劃書從頭到尾沒提過圖片怎麼存，Phase 2待辦清單也沒列，是一個真正的規劃空白，非本階段刻意排除的項目。

**採用方案：後端收檔案、存本機硬碟**（`POST /api/products/{id}/image`，`multipart/form-data`），並明確列為技術債，正式上架前應改用雲端物件儲存（S3／GCS等）。

考量過的三個方案：

| 方案 | 做法 | 優點 | 缺點 | 採用情況 |
|---|---|---|---|---|
| A. 雲端物件儲存 | 後端產生預簽章上傳網址，前端直接傳檔案到雲端 | 不吃自家伺服器頻寬與硬碟、天生有CDN、正式產品標準做法 | 需申請雲端帳號、有費用、多一個外部依賴 | 列為Phase 2待辦，正式上架前應採用 |
| **B. 後端存本機硬碟**（採用）| 開一個上傳端點收檔案，存進伺服器資料夾，Spring靜態資源機制對外開放 | 不需任何外部服務、雛型階段最快能動起來 | 多台伺服器時各自獨立不同步；容器化部署重建時硬碟內容可能消失，**不適合正式環境** | ✅本階段採用，明確為技術債 |
| C. 存進資料庫（Base64/BLOB）| 圖片二進位資料直接存進products表 | 不需外部依賴 | 每次查詢列表都拖著圖片資料，拖慢所有列表API；資料庫體積暴增 | 不採用，任何階段皆不建議 |

**技術實作要點**：

- 圖片實際存放於專案目錄下、`src/main/resources`**以外**的資料夾（例：`./uploads/products/`，路徑由`app.upload.dir`設定值控制），因為`resources`底下的內容會在build時打包進jar、唯讀，無法承載執行期才寫入的檔案
- 該資料夾需加入`.gitignore`，避免測試上傳的圖片被誤commit
- 對外的圖片網址走Spring內建靜態資源機制（`/images/products/**`），**公開讀取、不要求登入**（見下方安全性討論）

**安全性與實作複雜度討論**（四項必做＋三項技術債＋一項需明確拍板的取捨）：

| 風險 | 對策 | 複雜度 |
|---|---|---|
| 路徑穿越（信任使用者上傳檔名可能寫到目錄外）| 檔名一律由伺服器端產生（UUID），不採用客戶端原始檔名 | 低，必做 |
| 偽裝檔案類型（Content-Type Header可被客戶端造假）| 不能只看副檔名／Header，需用`ImageIO.read()`實際解碼內容確認是合法圖片 | 低（JDK內建），必做 |
| 塞爆硬碟（無大小限制）| `spring.servlet.multipart.max-file-size`設定上限（5MB）| 低，必做 |
| 替換圖片時DB指向不存在的檔案 | 寫入順序：先存新檔→更新DB指向新檔→最後才刪舊檔，任一步中途失敗最差只留孤兒檔案（無害）| 低，必做 |

刻意先不做、明確記錄為技術債：

| 項目 | 為什麼先不做 | 重新評估時機 |
|---|---|---|
| 上傳頻率限制（Rate Limiting）| 所有端點皆需登入，能濫用者僅限內部團隊帳號，風險範圍小；真做需引入額外套件，複雜度與風險不成比例 | 若系統開放給內部團隊以外的使用者 |
| EXIF中繼資料清除（手機照片常內嵌GPS座標）| 內部商品照片工具，非使用者個資照片 | 若允許終端消費者上傳照片（例如客訴附件）|
| 縮圖／多尺寸產生 | 效能優化而非安全性問題，原圖對雛型資料量已足夠 | 圖片數量/流量大到影響載入速度時 |

**需要明確拍板的取捨：圖片讀取是否要求登入。已決定採「公開讀取」**——理由：商品照片本來就不是機密資料（等同一般電商網站的商品圖，任何人都能複製圖片網址查看），檔名為UUID，無目錄列表功能，無法被列舉出完整清單；若要求登入才能讀取，需捨棄Spring內建靜態資源機制、另寫一支手動讀檔＋組裝Response的Controller，複雜度提高但對內部工具的實際效益不成比例。

**待確認事項**：`POST`／`PUT /api/products`的`imageUrl`欄位目前仍是一般字串欄位，未鎖定為唯讀，理論上仍可繞過上傳驗證直接塞入任意字串（例如外部圖床連結）。這是保留給開發測試階段的彈性，還是應該收斂成「只能透過上傳端點設定」，見十五-3。

3. **品項狀態矩陣不需全部照做**：只做核心路徑（未審核→已審核通過/拒絕→重新送審→未審核），封存/復用/刪除的完整後端檢查延後至Phase 2，前端先用隱藏按鈕處理
4. **Final Score凍結的雙軌計算是Week 1架構決策**：已審核通過商品分數凍結、未審核/拒絕商品正常重算，需在資料庫schema階段就定案
5. **評估模式版本鎖定**：管理層僅能於3套固定模式間單選切換生效模式（權重唯讀展示，不提供調整功能），不做版本歷史表，Snapshot只存模式名稱字串即可
6. **AI防呆測試不可省**：需針對資料完整度剛好卡在60%附近、部分欄位缺失的商品實際測試AI輸出，確認模型會明確表示「資料不足」而非虛構內容
7. **節慶因素的作用範圍需分兩階段理解**（純概念澄清，供回答評審提問用，不影響工時）：

   ```
   商品
   │
   ├── A. 尚未進入商品候選池
   │   └── 節慶因素 → 影響「找誰」（對應AI主動選品／發現階段）
   │
   └── B. 已經進入商品候選池
       └── 節慶因素 → 影響「排誰」（對應Festival Boost／排序階段）
   ```

   節慶檔期狀態理論上也可用於動態調整資料蒐集/趨勢同步的優先級與頻率，但雛型階段採用模擬市場資料集、非即時爬蟲，此機制僅列入Phase 2概念設計，本階段不實作、不編列工時。

8. **GET /api/products/{id} N+1風險**：此為聚合端點（同時取得商品基本資料、評估、趨勢、AI、風險等關聯資料），Spring Data JPA新手常見地雷。W1環境建置階段需針對此端點寫PoC並用SQL log驗證實際查詢數量，避免`@OneToMany`懶載入導致N+1，必要時改用`JOIN FETCH`或DTO投影一次查完。
9. **統一錯誤回應格式**：W1需定案全域例外處理（`@ControllerAdvice`）與統一Error Response格式（code/message/timestamp），這是W1基礎建設裡幾乎零成本就能定案的事，避免各API各自為政。
10. **JSON欄位JPA映射**：MySQL JSON型別（`matched_campaign_snapshot`／`weight_snapshot`／`product_snapshot`／`trend_snapshot`等）與Hibernate預設不原生支援物件映射，需要額外套件或`@Convert`手動處理，屬於真實已知的Java生態坑。W1需先做一個最小PoC，存一筆帶JSON欄位的資料、讀出來反序列化，確認技術路徑可行。
11. **任務依賴順序原則**（不涉及指名分工，實際4人分工待補，見十五-2）：
    ```
    DB schema定案（W1）→ 前後端才能平行開發
    API contract凍結時間點 → 需在W1結束前明訂
    評估/節慶邏輯 → 依賴DB schema，但可與前端框架平行進行
    審核流程 → 依賴評估邏輯先完成
    ```
12. **熔斷清單之後的第二層方案**（非正式緩衝，團隊心理準備用，不動熔斷清單本身工時計算）：例如LLM分析只做已核准商品的demo資料、節慶加成明細UI退化成純文字表格。
13. **後端Controller／Service分層決議**：

    ```
    Controller
    │
    ├── AuthController        → AuthService
    │       └── POST /api/auth/login、GET /api/auth/me、POST /api/auth/logout
    ├── UserController        → UserService
    │       └── GET /api/users、POST /api/users、PUT /api/users/{id}/disable
    ├── DashboardController   → DashboardService
    │       └── GET /api/dashboard/statistics、/recommendations、
    │           /risk-alerts、/conversion-rate
    ├── ProductController     → ProductService
    ├── ScoringController     → ScoringService
    │       └── GET /api/products/{id}/evaluation、
    │           GET /api/products/{id}/festival-boost
    ├── ReviewController      → ReviewService
    ├── TrendController       → TrendService
    ├── AiSelectionController → AiSelectionService
    └── SettingsController    → SettingsService
    ```

    - **`UserController`／`UserService`獨立於`AuthController`／`AuthService`**：`AuthService`負責的是「驗證我是誰」（登入、取得自身資料、登出），`UserService`負責的是「管理別人的帳號」（列出、新增、停用），權限範圍也不同（前者[操作+管理]、後者[僅管理]）。兩者僅共用`AppUser`實體與`app_users`資料表，不共用商業邏輯，合併會讓一個Service同時承擔「自身身分」與「他人帳號管理」兩種性質的職責。
    - **`ScoringService`從原規劃的`AiSelectionService`拆出**：六大分項＋Festival Boost＋Final Score屬於確定性加權計算，跟`AiSelectionService`負責的LLM推論（`ai_analyses`讀寫）性質不同（純函數運算 vs 外部API呼叫、失敗重試），合併會違反單一職責，且不利於分開撰寫單元測試。
    - **`POST /api/products/{id}/trend/sync`掛在`TrendController`**：觸發動作是「同步趨勢資料」，但方法內部需呼叫`ScoringService`觸發重算（Service間依賴，方向單向：`TrendService → ScoringService`，不可逆向依賴造成循環）。
    - **`ReviewService`透過呼叫`ScoringService`／`AiSelectionService`取得快照資料**，而非直接注入六、七個Repository——組裝Snapshot（`weight_snapshot`／`trend_snapshot`／`matched_campaign_snapshot`／`ai_summary_snapshot`）的細節封裝在對應Service內部，`ReviewService`只管審核流程本身（狀態機、風險勾選、留存快照）。
    - **新增`SettingsController`／`SettingsService`**，統一承接五、資料表設計中所有「設定類」CRUD（`product_types`／`evaluation_modes`／`evaluation_factors`／`audience_profiles`／`risk_options`／`festive_campaigns`／`system_settings`），避免這些端點被隨手塞進其他Controller導致邊界模糊。

14. **⚠️ 新增品項／自訂設定類資料，後端刻意不擋重複名稱，防重複點擊是前端職責**：
    `POST /api/products`（商品名稱）、`POST /api/settings/product-types`（分類名稱）、
    `POST /api/settings/risk-options`（風險選項名稱）這三支新增端點，後端刻意不檢查
    名稱是否重複（詳見五、資料表設計products.name欄位備註，與`ProductService.
    createProduct()`程式碼註解）——同名在業務上可能合法存在（例如不同供應商的
    同名商品），後端用「一律禁止同名」的規則會連帶擋掉合法情境。
    **前端必須自行處理「使用者手滑重複送出同一筆」的風險**（送出後禁用按鈕、
    debounce、或偵測到同名時跳出確認提示），這不是後端疏漏，是刻意的責任劃分，
    開發時不要假設後端會擋。若某張表未來確認名稱必須唯一，需要後端應用層查詢
    檢查＋DB層UNIQUE約束兩者一起補上，屆時再回頭修改。

## 十五、待決議事項

> 本章只列**目前仍未定案、需要決策才能推進**的項目。已定案的決議一律寫回所屬正規章節（欄位設計進五、資料表設計，UI細節進二、前端功能樹狀圖，技術選型進六、QA摘要或七、設計決議），不在本章重複保留，避免同一件事散落兩處、日後修改時漏改其一。

### 15-1 品項詳情頁工時未獨立估算（風險提醒）

品項詳情頁有14個子區塊、多種條件式渲染狀態（Loading／Empty／Error等），目前工時分散在「9-1核心7項」的商品建立（2天）、基礎評估分數計算（2.5天）、節慶加成機制（3.5天）等項目裡，沒有獨立估算，可能被低估。

**需要決定**：是否在W3進度檢查點實際盤點品項詳情頁完成度後，再決定要不要調整後續排程或啟動熔斷清單。

**本文件的建議**：不現在重新拆分總天數——拆分不會改變實際工作量，只是換一種記帳方式；改為在W3檢查點以「品項詳情頁14個子區塊完成幾個」作為具體觀測指標，落後再啟動熔斷。

### 15-2 4人分工圖／實際人員技能分佈

25天總工時目前僅有「任務依賴順序原則」（見十三-11），沒有依「A負責什麼、B負責什麼」的實際分工表。

**需要提供**：4人各自的技能分佈（誰較熟前端、誰較熟後端）與初步分工意向，才能把依賴順序原則具體化成可用的分工表。

**未提供前的影響**：排程只能停留在「哪些任務不能並行」的層級，無法估算個別成員的負載是否平均，也無法及早發現「某人身上壓了三個關鍵路徑任務」這類風險。

### 15-3 imageUrl是否要收斂成僅能透過上傳端點設定

目前`POST`／`PUT /api/products`的`imageUrl`仍是一般字串欄位（見五-2欄位備註），與`POST /api/products/{id}/image`（驗證過的檔案上傳）並存，代表繞過驗證直接塞入任意字串（含外部圖床連結）目前技術上是可行的。

**需要決定**：這個彈性是刻意保留（例如demo階段想快速外連一張現成的網路圖片，不想每次都走上傳流程），還是應該收斂成「圖片只能透過上傳端點設定」，把`imageUrl`從兩支DTO移除、改為唯讀（僅能由後端寫入）。

**兩者的實際差異**：保留彈性=開發測試方便，但`image_url`存的內容不再保證「一定是通過驗證的合法圖片」；收斂=一致性更好，但少了快速外連圖片測試的彈性。哪個影響較大取決於demo流程的實際需求。
