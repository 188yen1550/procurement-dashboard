# AI選品決策輔助系統｜完整規格書

> 本文件為單一版本的完整規格彙整，不含版本演進比較，供W1（第一週）資料庫schema定案與後續開發直接參照。

## 一、系統定位（不變的最高原則）

> **系統只負責「整理資料、給建議」，商品最終要不要賣，永遠由人來按下核准。**

```
資料蒐集 → 規則式評估 → 加權計分 → AI輔助分析 → 人工審核 → 正式選品決策
```

AI的角色僅限於：趨勢資料分析、AI摘要、推薦原因、風險提示、核心客群匹配輔助、協助發現潛在候選商品。**最終核准與否，永遠由人工審核決定。**

### ⚠️ 重要提醒：核准（APPROVED）≠ 已銷售

`review_status`（審核狀態欄位）中的`APPROVED`（已審核通過）僅代表：**此商品通過選品評估與人工審核，被列入可執行團購銷售的候選名單**。

它**不代表**：已正式上架銷售／已與供應商完成議價或簽約／已產生實際訂單或營收。

「核准」是本系統**選品決策的終點**，不是**銷售執行的起點**。核准後的議價、上架、實際開團等商業動作，屬於團購營運下一階段的決策範疇，不在本系統範圍內。此定義需在儀表板、審核頁UI文案、以及demo口頭說明中一致呈現。

### ⚠️ 命名區隔提醒：`pricing_type` vs `product_type_id`

兩個欄位中文都可能被稱為「商品類型」，但語意完全不同，開發與文件中須嚴格區分：

| 欄位 | 代表意義 | 值 |
|---|---|---|
| `pricing_type` | 訂價分流（QA1原始設計） | `NEW`（新品）／`RESALE`（再販售） |
| `product_type_id` | 商品實際分類（架構v3原始設計） | FK關聯`product_types`表，例如食品/日用品等 |

`pricing_type`為避免與`product_type_id`混淆而特別命名，非架構v3原始欄位名稱。

## 三、API總表

> 每支API均標示角色權限：`[操作+管理]`代表操作／管理皆可呼叫；`[僅管理]`代表僅MANAGER角色可呼叫，後端須以Spring Security `@PreAuthorize`等method security機制落實，不可僅靠前端選單隱藏（見六-4安全性備註）。

```
API
│
├── 1. 登入／權限
│   ├── POST /api/auth/login [公開，無需登入]
│   │   └── 功能：驗證帳號密碼、建立JWT Token、取得使用者角色
│   ├── GET /api/auth/me [操作+管理]
│   │   └── 功能：取得目前登入使用者的基本資料與角色
│   └── POST /api/auth/logout [操作+管理]
│       └── 功能：登出，前端清除本地Token；為未來若需token黑名單機制預留擴充點
│
├── 2. 儀表板
│   ├── GET /api/dashboard/statistics [操作+管理]
│   │   └── 功能：取得商品總數、待審核數、通過數、拒絕數等統計
│   ├── GET /api/dashboard/recommendations [操作+管理]
│   │   └── 功能：依Final Score取得推薦分數較高的前10項商品，含重新入榜標籤
│   ├── GET /api/dashboard/risk-alerts [操作+管理]

### 2. products（商品資料表）

```
├── id(BIGINT、PK)：商品唯一識別碼
├── product_type_id(BIGINT、FK、NOT NULL)：對應商品類型(product_types)
├── pricing_type(ENUM、NOT NULL)：商品分流【QA1新增】
│   ├── NEW：新品
│   └── RESALE：再販售
├── name(VARCHAR(100)、NOT NULL)：商品名稱
├── description(TEXT)：商品基本說明
├── image_url(VARCHAR(500))：商品圖片位置
├── supplier_name(VARCHAR(100))：供應商名稱
├── cost_price(DECIMAL(10,2)、NULLABLE)：商品成本價格
│   └── 備註：新品(NEW)可為空，待議價完成後回填【QA1】
├── sale_price(DECIMAL(10,2)、NULLABLE)：預計銷售價格
│   └── 備註：新品(NEW)可為空【QA1】
├── market_price(DECIMAL(10,2)、NULLABLE)：市售價格（消費者一般通路購買價）【十四-1新增】
│   └── 備註：僅RESALE商品填寫，NEW商品不適用；不進評分公式，僅供品項詳情頁
│       「市價與團購價比較」區塊呈現折扣率(QA2)
├── campaign_tags(VARCHAR(255)、NULLABLE)：節慶標籤【新增】
│   └── 備註：逗號分隔字串(例："bbq,gift")，與festive_campaigns.target_tags做交集比對
├── moq(INT)：最低訂購量
├── supply_stability(DECIMAL(5,2))：供應穩定性評估資料
├── price_competitiveness(DECIMAL(5,2))：商品價格競爭力評估資料
├── target_customer_description(TEXT)：商品適合客群的補充描述
├── estimated_purchase_rate(DECIMAL(5,2))：預估消費者購買商品的可能性
├── review_status(ENUM、NOT NULL)：審核狀態
│   ├── PENDING：未審核
│   ├── REJECTED：已審核拒絕
│   └── APPROVED：已審核通過（⚠️不代表已銷售，見一、系統定位）
├── candidate_status(ENUM、NOT NULL、DEFAULT CANDIDATE)：候選狀態【QA4新增，DEFAULT值已修正】
│   ├── AI_SUGGESTED：AI建議，非正式候選（僅由AI批次選品產生，見POST /api/products/ai-suggested/batch-generate）
│   └── CANDIDATE：正式候選，進入評分排行
├── pricing_status(ENUM、NULLABLE)：訂價狀態【QA1新增，補上PRICED狀態與轉換規則】
│   ├── PENDING_PRICING：新品(NEW)待訂價
│   ├── PRICED：新品(NEW)已完成議價定價
│   │   └── 轉換規則：Service層於PUT /api/products/{id}寫入當下檢查，
│   │       若pricing_type=NEW且cost_price與sale_price皆非NULL，
│   │       自動將pricing_status由PENDING_PRICING轉為PRICED（無需額外API，寫入時自動判斷觸發）
│   └── 備註：此欄位為NULLABLE，僅NEW商品才會有值（PENDING_PRICING/PRICED），
│       RESALE商品固定留空（NULL不是ENUM合法成員，此處留空僅代表「此欄位對RESALE商品無意義」）
├── item_status(ENUM、NOT NULL)：品項是否啟用
│   ├── ACTIVE：使用中
│   └── ARCHIVED：已封存
├── submission_count(INT、NOT NULL、DEFAULT 0)：第幾次送審
├── created_by(BIGINT、FK)：建立商品的使用者

├── updated_at(DATETIME、NOT NULL)
└── updated_by(BIGINT、FK)：最後修改商品的使用者
```

### 4. evaluation_modes（評估模式版本表）

```
├── id(BIGINT、PK)：評估模式版本唯一識別碼
├── mode_code(VARCHAR(30)、NOT NULL)：評估模式代碼
│   ├── BALANCED：均衡模式
│   ├── VOLUME：衝量模式

└── created_by(BIGINT、FK)
```

**核心概念**：權重修改不覆蓋既有資料，而是建立新版本，確保歷史審核結果可追溯。

**3套模式權重草案**（供審核，非依實際銷售數據校準）：

| 模式 | BUSINESS | AUDIENCE | HISTORY | FORECAST |
|---|---|---|---|---|
| 均衡模式(BALANCED) | 25% | 25% | 25% | 25% |
| 衝量模式(VOLUME) | 15% | 30% | 15% | 40% |
| 高利潤模式(PROFIT) | 45% | 15% | 15% | 25% |

### 5. evaluation_factors（評估因子表）

```
├── id(BIGINT、PK)：評估因子唯一識別碼
├── evaluation_mode_id(BIGINT、FK、NOT NULL)：所屬評估模式版本
├── factor_code(VARCHAR(50)、NOT NULL)：評估因子系統識別代碼
├── factor_name(VARCHAR(100)、NOT NULL)：評估因子顯示名稱
├── category(VARCHAR(50)、NOT NULL)：評估因子大分類
│   ├── BUSINESS：商品商業條件
│   ├── AUDIENCE：核心客群匹配度
│   ├── HISTORY：歷史銷售資料
│   └── FORECAST：預測人氣（對應product_evaluations.forecast_score，聚合purchase_score與trend_score，各占50%子權重）
├── weight(DECIMAL(5,2)、NOT NULL)：固定權重
├── description(VARCHAR(255))：因子說明

### 節慶加成計分規則

```
Final Score = Base Score + Festival Boost
Festival Boost = Match Weight × Urgency Factor × Boost Cap上限（暫訂+5，絕對分數）
```

- **Match Weight**（標籤命中權重係數）：核心命中1.0／一般命中0.6／弱命中0.3／未命中0，多標籤取最高等級不加總
- **Urgency Factor**（時間緊迫係數）：
  - 節日型(FESTIVAL)：PREPARING期間線性遞增(1－剩餘天數/準備天數)，ACTIVE固定1.0
  - 季節型(SEASON)：PREPARING固定0.2（不遞增），ACTIVE固定1.0
- **多節慶重疊**：取最大值(MAX)，不加總套Cap
- **不命中不扣分**：Festival Boost=0，不影響原本評分
- **已審核通過商品**：Final Score凍結於Snapshot，不隨後續趨勢更新重算
- **命中判定**：商品`campaign_tags`與當前啟用檔期`target_tags`做集合交集運算(split(",")後比對)，有交集即判定命中；**僅比對`campaign_status IN (PREPARING, ACTIVE)`的檔期**，`UPCOMING`（尚未備戰）與`EXPIRED`（已結束）的檔期不參與Festival Boost計算，即使標籤有交集也視為未命中

## 五、QA修正落地設計摘要

### QA1｜毛利判定邏輯（新品 vs 再販售）

`pricing_type`：`NEW`（新品）／`RESALE`（再販售）。新品不要求成本價/售價欄位，狀態為`PENDING_PRICING`（待訂價），評分引擎以該類別歷史中位數代入，不因欄位空白被扣分；再販售正常帶入定價欄位並計算毛利率。

### QA2｜市售價格 vs 團購價格的吸引力評估

不疊加進總分公式（避免跟毛利率因子重複計分），做成品項詳情頁AI分析區塊的呈現層量化洞察（折扣率、消費者實際入手成本）。所需的「市售價格」欄位已定案為`products.market_price`，僅RESALE商品填寫，見十四-1。

### QA3｜資料完整度60%門檻的計算範圍

門檻分母只計算操作層建立商品當下有能力自主填齊的欄位，依`pricing_type`動態調整；未達門檻不進入固定評估模式計分、不進入AI推薦Top10，列表狀態顯示「資料待補」，仍允許編輯補齊。

### QA4｜AI主動選品的定位

`candidate_status`：`AI_SUGGESTED`（AI建議，非正式候選，僅由AI批次選品排程產生）→ 操作人員手動「加入候選」→ `CANDIDATE`（正式候選，才進入評分排行）。**操作人員手動新增品項預設直接為`CANDIDATE`**（非AI_SUGGESTED，修正原設計語意矛盾——手動輸入的商品不是「AI建議」）。只有`CANDIDATE`狀態商品才會出現在品項清單、分數排行、推薦清單裡。

### QA5｜本地LLM vs API串接LLM

**結論：維持API串接**，團隊規模與時程都不具備自架LLM的條件；搭配「AI內容預先生成並快取」機制因應現場風險。**廠商已定案為GPT-5.6 Luna**（OpenAI GPT-5.6系列最低成本版本，Input $0.20／1M、Output $1.20／1M tokens，支援Structured Outputs／Function Calling，標準API Key認證），月度預算上限$20美金以下（見十四-2）。架構上仍以Service層抽象介面（例如`LlmAnalysisService`）隔離廠商依賴，換模型只需改一個實作類別，不因廠商已定案而放棄此抽象層。

**已知限制（刻意技術債）**：`risk_options`／`evaluation_modes`目前只有讀取（GET）API，沒有對應的管理UI／寫入API可供操作，本階段新增或調整這兩張表的資料一律採直接改DB種子值（seed script）方式處理，不現在開發新增用UI，待Phase 2視實際需求評估是否要補管理介面。

## 六、風險示警與決策回饋設計決議

### 6-1 三項功能的效益/複雜度比較

| 功能 | 效益 | 複雜度 | 原始工時估算 |
|---|---|---|---|
| 風險示警中心（獨立監控系統） | 中，但demo現場很難剛好展示到觸發時刻 | 高（規則引擎+排程+UI） | 4-5天 |
| 決策紀錄與回饋閉環 | **最高**，是驗證「AI輔助決策」定位的證據來源 | 中偏高 | 3-4天（簡化版） |
| 報表中心 | 最低，demo現場很少被檢視 | **最高**（PDF中文字型是Java生態老坑） | 3-4天（且風險不可控） |

### 6-2 最終決議：風險示警中心（獨立監控系統）不做

改用AI風險提示（唯讀顯示於品項詳情）→ 管理層審核時閱讀 → 人工風險評估（複選）→ 審核留言，風險溝通在審核當下一次處理完，不需要獨立、24小時背景運作的示警系統。改用「已審核拒絕商品重新入榜提醒」機制取代其展示效果（見二、前端功能樹狀圖之AI推薦Top10）。

### 6-3 決策紀錄（保留）

`review_records`本來就是審核功能的必要產物，真正的增量成本只有一個「決策紀錄列表」查詢畫面。**準確度統計分析（如Pearson相關係數、A級命中率%）不做**——雛型階段樣本數不足，留待Phase 2累積真實資料後再做。

### 6-4 安全性設計（RBAC落實／併發控制／JWT）

**RBAC後端落實**：三、API總表已逐支標示`[操作+管理]`／`[僅管理]`角色權限，前端選單隱藏僅是體驗優化，**後端須以Spring Security method security（如`@PreAuthorize("hasRole('MANAGER')")`）逐支落實**，避免Broken Access Control（OWASP API1/API5）風險，尤其`POST /api/reviews`與所有`/api/settings/*`必須鎖死僅`MANAGER`角色可呼叫。此為W1「登入/RBAC」既有工時範圍內的必要工作項，非新增工時。

**審核併發控制**：`POST /api/reviews`寫入前，Service層以條件式UPDATE（`UPDATE products SET review_status=? WHERE id=? AND review_status='PENDING'`）更新狀態，若影響筆數為0（代表已被他人審核過）回傳409 Conflict，避免同一品項被重複審核造成狀態競態。**不採用樂觀鎖版本欄位**（不新增`products.version`），因為完整樂觀鎖需要前後端配套的版本傳遞與衝突處理UI，對6週時程屬於過度工程化；條件式UPDATE可達到同等防護效果，且僅需Service層一行SQL改動。

**JWT設定**：

| 決策項目 | 採用方案 |
|---|---|
| Token儲存位置 | httpOnly Cookie優先；若實作複雜度過高可退而求其次採記憶體內變數，**不使用**localStorage/sessionStorage（防XSS竊取） |
| 過期時間 | 8小時（對應一個工作天），demo環境可視情況調整 |
| Refresh Token | **不實作**完整輪替機制，過期後直接要求重新登入，避免正式產品級複雜度（黑名單/輪替偵測），列入Phase 2待辦 |
| 登出端點 | 補上`POST /api/auth/logout`，即使JWT本質無狀態、單純登出效果有限，仍維持語意完整性並為未來黑名單機制預留擴充點 |
| DB Schema影響 | 不需新增欄位，維持JWT無狀態設計 |
| Token過期流程 | 任何頁面偵測到401 → 導回登入頁＋保留原本操作提示（例如「請重新登入後繼續操作」），呼應8小時過期、無Refresh Token的設定 |

## 十二、其他架構細節提醒（避免範圍漏接）

1. **儀表板「高風險示警」卡片**：改用AI風險提示文字關鍵字比對取得資料來源（見四、risk_options.alert_keywords）
2. **重新送審流程是重新入榜提醒的前置依賴**：需在Week 1 schema設計時就規劃`submission_count`欄位
3. **品項狀態矩陣不需全部照做**：只做核心路徑（未審核→已審核通過/拒絕→重新送審→未審核），封存/復用/刪除的完整後端檢查延後至Phase 2，前端先用隱藏按鈕處理
4. **Final Score凍結的雙軌計算是Week 1架構決策**：已審核通過商品分數凍結、未審核/拒絕商品正常重算，需在資料庫schema階段就定案
5. **評估模式版本鎖定**：管理層僅能於3套固定模式間單選切換生效模式（權重唯讀展示，不提供調整功能），不做版本歷史表，Snapshot只存模式名稱字串即可
6. **AI防呆測試不可省**：需針對資料完整度剛好卡在60%附近、部分欄位缺失的商品實際測試AI輸出，確認模型會明確表示「資料不足」而非虛構內容
7. **節慶因素的作用範圍需分兩階段理解**（純概念澄清，供回答評審提問用，不影響工時）：

   ```
   商品
   │
   ├── A. 尚未進入商品候選池
   │   └── 節慶因素 → 影響「找誰」（對應AI主動選品／發現階段）
   │
   └── B. 已經進入商品候選池
       └── 節慶因素 → 影響「排誰」（對應Festival Boost／排序階段）
   ```

   節慶檔期狀態理論上也可用於動態調整資料蒐集/趨勢同步的優先級與頻率，但雛型階段採用模擬市場資料集、非即時爬蟲，此機制僅列入Phase 2概念設計，本階段不實作、不編列工時。

8. **GET /api/products/{id} N+1風險**：此為聚合端點（同時取得商品基本資料、評估、趨勢、AI、風險等關聯資料），Spring Data JPA新手常見地雷。W1環境建置階段需針對此端點寫PoC並用SQL log驗證實際查詢數量，避免`@OneToMany`懶載入導致N+1，必要時改用`JOIN FETCH`或DTO投影一次查完。
9. **統一錯誤回應格式**：W1需定案全域例外處理（`@ControllerAdvice`）與統一Error Response格式（code/message/timestamp），這是W1基礎建設裡幾乎零成本就能定案的事，避免各API各自為政。
10. **JSON欄位JPA映射**：MySQL JSON型別（`matched_campaign_snapshot`／`weight_snapshot`／`product_snapshot`／`trend_snapshot`等）與Hibernate預設不原生支援物件映射，需要額外套件或`@Convert`手動處理，屬於真實已知的Java生態坑。W1需先做一個最小PoC，存一筆帶JSON欄位的資料、讀出來反序列化，確認技術路徑可行。
11. **任務依賴順序原則**（不涉及指名分工，實際4人分工待補，見十四-4）：
    ```
    DB schema定案（W1）→ 前後端才能平行開發
    API contract凍結時間點 → 需在W1結束前明訂
    評估/節慶邏輯 → 依賴DB schema，但可與前端框架平行進行
    審核流程 → 依賴評估邏輯先完成
    ```
12. **熔斷清單之後的第二層方案**（非正式緩衝，團隊心理準備用，不動熔斷清單本身工時計算）：例如LLM分析只做已核准商品的demo資料、節慶加成明細UI退化成純文字表格。

## 十四、待確認事項（需使用者補充資料，非本文件臆測）

### 14-1「市售價格」欄位（已定案）

**決議**：新增`market_price`（DECIMAL(10,2)、NULLABLE）欄位。僅`RESALE`（再販售）商品需填寫，`NEW`（新品）商品不適用（新品尚未有實際市場對照價格）。此欄位不進入評分公式（QA2已定案：呈現層量化洞察，不疊加進總分），僅供品項詳情頁「市價與團購價比較」區塊使用。

**判斷依據**：`cost_price`（成本價）是B2B進貨成本，`sale_price`（預計銷售價格）是團購賣價，兩者語意上都不等於「消費者一般通路購買價格」。若借用既有欄位overload雙重語意，會造成日後API/UI/報表難以區分情境，故獨立新增欄位。已同步更新第四章`products`表schema定義（見下方14-6欄位增補摘要）。

### 14-2 LLM廠商與預算（已定案）

**決議**：
- 廠商：**GPT-5.6 Luna**（OpenAI GPT-5.6系列最低成本/最快速版本）
- 定價（查證日期2026/08）：Input $0.20／1M tokens、Output $1.20／1M tokens、快取輸入$0.02／1M tokens；支援Structured Outputs/JSON Mode與Function Calling，認證方式為標準API Key
